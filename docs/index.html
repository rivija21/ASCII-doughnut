Inside ASCII Sims

Four animations drawn with nothing but text characters in a terminal: a 3D donut that flies and pops, Matrix rain, Doom fire and a chaotic double pendulum. This guide explains how the C++ is put together, and the maths and physics inside each animation.

Every terminal on this page is live. Each one runs the program’s own algorithm, ported line by line from C++ to JavaScript, so you can poke at it here and then find the same lines in the source.

Simulation 1 from the menu, running live. Each time it swoops through the middle of the 8 it pulses like a drop hitting water; Space pulses it whenever you like. M switches between flying and the original spin in place, and the donut glides between the two.

Run it

On a Mac, double-click Run ASCII Sims.command in the project folder. It opens Terminal, builds the program the first time (and again whenever the code changes), makes the window 140 × 44 characters and starts it. From Terminal you can also do it by hand:

./build.sh      # compile with Apple's clang
./ascii-sims    # run

On Windows, run build.bat, then ascii-sims.exe in Windows Terminal. Both systems compile the same files except one: each build script picks either platform_mac.cpp or platform_windows.cpp (see two operating systems).

The program

main.cpp · sim.h

The loop

Every animation, in every game engine, is the same loop: read the keys, move the world forward, draw it, show it, wait, and go round again. At 30 frames per second one trip round takes 33 milliseconds.

dt is capped at 0.1 s. If you drag the window and the program stalls for a second, the physics moves on 0.1 s instead of jumping a whole second at once.
src/main.cppvoid runSimulation(Simulation& sim) {
    Canvas cv;
    FrameClock clock(kFps);
    int lastW = -1, lastH = -1;
    bool paused = false;
    double dt = 0;

    while (true) {
        // 1. Handle a resized window.
        int w, h;
        term::size(w, h);
        if (w != lastW || h != lastH) {
            lastW = w;
            lastH = h;
            cv.resize(w, h);
            if (!tooSmall(w, h)) sim.resize(w, h - 1);   // the last row is the status bar
            term::clearScreen();
        }

        // 2. Input.
        for (int k = term::readKey(); k != KEY_NONE; k = term::readKey()) {
            if (k == 'q' || k == KEY_ESC) return;
            if (k == 'p')
                paused = !paused;
            else
                sim.onKey(k);
        }

        // 3. Update, 4. draw, 5. show.
        cv.clear();
        if (tooSmall(w, h)) {
            drawTooSmall(cv);
        } else {
            // Clamp dt: if the window was dragged and the program stalled for a second,
            // we don't want the physics to jump a whole second in one go.
            if (!paused) sim.update(std::min(dt, 0.1));
            sim.draw(cv);
            drawStatusBar(cv, sim, clock.fps(), paused);
        }
        cv.present();

        // 6. Wait for the next frame.
        dt = clock.tick();
    }
}

One interface, four animations

src/sim.hclass Simulation {
public:
    virtual ~Simulation() = default;
    virtual const char* name() const = 0;
    virtual const char* help() const = 0;   // key hints shown in the status bar
    virtual void resize(int w, int h) = 0;
    virtual void onKey(int key) = 0;
    virtual void update(double dt) = 0;
    virtual void draw(Canvas& cv) = 0;
};

= 0 makes a function pure virtual: Simulation itself is only a promise that anything which is a Simulation can do these six things. Donut, MatrixRain, Fire and DoublePendulum each inherit from it and override them.

update changes, draw looks. update(dt) moves the state on; draw() only reads it. Pausing is simply not calling update(), and the physics never depends on how often the screen is redrawn.

runSimulation(Simulation& sim) calls sim.update(dt) without knowing which kind of simulation it has. At run time C++ follows a hidden table of function pointers inside the object, the vtable, to the right version. That is polymorphism, and it is why adding a fifth animation means writing one new class and one new line in the menu.

Each .cpp file hides its class inside an anonymous namespace, so no other file can see it, and exposes only a factory such as makeDonut() that returns a std::unique_ptr<Simulation>. The unique_ptr owns the object and deletes it automatically when you go back to the menu. The menu itself is a table: each row holds a key, a title and a pointer to a factory function.

Variable and fixed time steps

dt is how many seconds really passed since the last frame: about 0.033, but never exactly. The donut and the Matrix rain use it directly, as in angle += speed * dt. The fire and the pendulum can’t, because the fire’s rule and the pendulum’s RK4 maths both assume every step is the same size. So they save time up and spend it in equal chunks:

src/fire.cppvoid update(double dt) override {
    leftover_ += dt;
    while (leftover_ >= kStep) {
        leftover_ -= kStep;
        step();
    }
}

The terminal is a frame buffer

terminal.h · terminal.cpp

Characters are pixels. Each terminal cell holds one character in one colour, and a cell is about twice as tall as it is wide, so every simulation squashes its y coordinates by half (or doubles x). Otherwise circles come out as tall ovals.

Canvas is a std::vector<Cell> with w × h entries: one flat array stored row by row, so cell (x, y) lives at index y * w + x. A simulation draws a whole frame into it, then present() turns the grid into one string and writes it in one go. Printing character by character would show half-finished frames, which is flicker.

The string mixes the visible characters with ANSI escape codes: text that starts with the ESC character (byte 27), which the terminal obeys instead of printing.

Two small tricks keep that string short. present() sends a colour code only when the colour changes, and never for a space, which is invisible anyway. And the simulations round their colours to 12–32 fixed levels, so neighbouring cells often share exactly the same colour. It also skips the bottom-right cell, because writing there makes some terminals scroll everything up a line.

src/terminal.cppvoid Canvas::present() {
    const bool rgb = platform::trueColour();
    out_.clear();
    out_ += "\x1b[?2026h";
    char buf[32];
    bool haveColour = false;
    Color current;
    for (int y = 0; y < h_; ++y) {
        int n = std::snprintf(buf, sizeof buf, "\x1b[%d;1H", y + 1);
        out_.append(buf, n);
        for (int x = 0; x < w_; ++x) {
            // Writing the bottom-right cell makes some consoles scroll everything up a line.
            if (y == h_ - 1 && x == w_ - 1) break;
            const Cell& c = cells_[y * w_ + x];
            // Only send a colour code when it changes. Spaces are invisible, so they never need one.
            if (c.ch != ' ' && (!haveColour || c.fg != current)) {
                n = rgb ? std::snprintf(buf, sizeof buf, "\x1b[38;2;%d;%d;%dm", c.fg.r, c.fg.g, c.fg.b)
                        : std::snprintf(buf, sizeof buf, "\x1b[38;5;%dm", nearest256(c.fg));
                out_.append(buf, n);
                current = c.fg;
                haveColour = true;
            }
            out_ += c.ch;
        }
    }
    out_ += "\x1b[?2026l";
    platform::write(out_);   // one big write per frame = no flicker
}

Older terminals: 256 colours

Apple’s Terminal only learned 24-bit colour in macOS 26. For older versions platform_mac.cpp notices, from the TERM_PROGRAM_VERSION environment variable, and present() sends ESC[38;5;nm instead. n picks one of 256 fixed colours: a 6 × 6 × 6 cube whose channels can only be 0, 95, 135, 175, 215 or 255, plus 24 greys from 8 to 238. nearest256() picks whichever is closest. Raw mode. A terminal normally works a line at a time (canonical mode): it shows what you type, lets you edit it, and only hands the line over when you press Return. tcgetattr() reads the terminal’s settings and tcsetattr() changes them. The program turns off ICANON (a line at a time) and ECHO (showing keys), and sets VMIN = 0 and VTIME = 0, which makes read() return straight away when no key is waiting. It saves the original settings and puts them back at the end.

src/platform_mac.cppvoid enterAnimationMode() {
    termios raw = originalSettings;
    raw.c_lflag &= ~(ICANON | ECHO);   // keys arrive one at a time as they're pressed, not shown
    raw.c_iflag &= ~IXON;              // otherwise Ctrl+S freezes the output until Ctrl+Q
    raw.c_cc[VMIN] = 0;                // read() returns at once, even when no key is waiting
    raw.c_cc[VTIME] = 0;
    tcsetattr(STDIN_FILENO, TCSANOW, &raw);
    writeAll(kEnterCodes, sizeof kEnterCodes - 1);
}
One file, two kinds of Mac. build.sh compiles with -arch arm64 -arch x86_64: a universal program that runs natively on Apple-chip and Intel Macs.

Arrow keys are escape codes too. Up arrives as three bytes, ESC [ A; Down, Right and Left end in B, C and D. Some terminals send ESC O A instead, and Shift+Up is ESC [ 1 ; 2 A. So when readKey() sees an ESC, it waits up to 20 ms (with poll()) for more bytes. If none come, it was the Esc key.

src/platform_mac.cppint term::readKey() {
    const int c = readByte();
    if (c < 0) return KEY_NONE;
    if (c != KEY_ESC) return std::tolower(c);

    const int next = readByteSoon();
    if (next != '[' && next != 'O') return KEY_ESC;
    // Skip any numbers and ';' (Shift+Up is ESC [ 1 ; 2 A) up to the final letter.
    int last;
    do {
        last = readByteSoon();
    } while (last >= 0 && (last < 0x40 || last > 0x7e));
    switch (last) {
        case 'A': return KEY_UP;
        case 'B': return KEY_DOWN;
        case 'C': return KEY_RIGHT;
        case 'D': return KEY_LEFT;
        default: return KEY_NONE;   // some other special key (F1, Home...): ignore it
    }
}
Tested in a pseudo-terminal: all three arrow forms, Esc, Ctrl+C, kill, Ctrl+Z then fg, and the 256-colour fallback. After quitting, stty -a matched its output from before the program started.

Signals. On a Mac, Ctrl+C reaches the program as a signal, SIGINT. Closing the window sends SIGHUP, and kill sends SIGTERM. A signal handler can run in the middle of anything, even halfway through allocating memory, so it may only call async-signal-safe functions such as write() and tcsetattr(). printf and std::string are off limits, which is why the restore codes are plain const char arrays.

src/platform_mac.cppvoid onQuitSignal(int sig) {
    term::restore();
    signal(sig, SIG_DFL);
    raise(sig);
}

Ctrl+Z sends SIGTSTP, which pauses the program and drops you back at the shell prompt. onSuspend() gives the shell a normal terminal first and stops. When you type fg it carries on from the line where it stopped and switches back into animation mode; the next frame repaints every cell.

[1]The flying donut

donut.cpp

After Andy Sloane’s donut.c (2006). The recipe for one frame: sample thousands of points on the surface of a torus, rotate them in 3D, move them to wherever the donut is, project them onto the grid, keep only the point nearest the viewer in each cell, and pick a character whose amount of ink matches how brightly that point is lit.

Press M to switch to the classic spin in place. A test compared that mode with the original program and found the same characters, frame for frame.

Build a torus out of points

Take a small circle of radius R1 = 1 whose centre is R2 = 2 from the Y axis, and spin it around that axis. θ (theta) goes round the small circle and φ (phi) spins the circle round the axis. A point on the circle, and the normal there (an arrow of length 1 pointing straight out of the surface, which the lighting needs), are:

P(θ)=(R2+R1cos⁡θ,R1sin⁡θ,0)N(θ)=(cos⁡θ,sin⁡θ,0)

Rotate it

Every rotation in 3D is a 2D rotation of two of the coordinates, leaving the third alone. Around the X axis by an angle A:

(x′y′z′)=(1000cos⁡A−sin⁡A0sin⁡Acos⁡A)(xyz)

Each point turns around Y by φ (that builds the donut), then around X by A and around Z by B (that tumbles it), and finally moves by the donut’s centre c. A and B grow at 1.2 and 0.6 radians per second; since one is exactly twice the other, the tumble repeats every 2π / 0.6 ≈ 10.5 seconds.

The normal gets the same three rotations, because it is attached to the surface, but it is never moved: it is a direction, not a place. Rotation stores a cosine and a sine together, because computing them is slow next to + and *, and the φ values are the same for every θ, so their cosines and sines are worked out once per frame into phiTable_.

Project it onto the grid

The eye sits at the origin looking along +z. By similar triangles, a point (x, y, z) lands on the grid at

sx=w2+K1xzsy=h2−12K1yz

Dividing by z is what makes far things small. The minus sign is there because rows count downwards, and the ½ squashes y for the tall cells. K1 is a zoom factor, chosen so that a donut K2 = 5 away fills about three quarters of the window:

K1=size·K2·38(R1+R2),size=min(w,2h)

Hide the back, light the front

The finished frame: the nearest point in each cell, shaded by how much it faces the light.

The z-buffer. Many points land in the same cell, for instance one on the front of the donut and one on the back. Only the nearest should show. zbuf_ remembers, for every cell, 1/z of the nearest point drawn so far. Storing 1/z means “nothing yet” can simply be 0, and bigger means closer. Every 3D game does this on the graphics card, for every pixel. Switch the panel to Depth to see the buffer itself, and to No z-buffer to see what happens without it.

src/donut.cppfor (float theta = 0; theta < kTwoPi; theta += thetaStep) {
    const Rotation t(theta);
    // A point on that small circle, sitting R2 to the right of the centre...
    const Vec3 circlePoint{R2 + R1 * t.c, R1 * t.s, 0};
    // ...and the surface normal there (an arrow pointing straight out of the surface).
    const Vec3 circleNormal{t.c, t.s, 0};

    // ...and phi spins that small circle around the Y axis, sweeping out the whole donut.
    for (const Rotation& p : phiTable_) {
        // Build the donut (rotate by phi), tumble it (rotate by A, then by B), swell it by s, then
        // move it to where it is. The normal is a direction, not a place: it only turns.
        const Vec3 point = s * rotateZ(rotateX(rotateY(circlePoint, p), rotA), rotB) + c;
        const Vec3 normal = rotateZ(rotateX(rotateY(circleNormal, p), rotA), rotB);

        // Perspective projection: things further away (bigger z) look smaller.
        const float ooz = 1.0f / point.z;   // "one over z": bigger means closer to the viewer
        const int sx = int(w_ / 2.0f + K1 * ooz * point.x);
        const int sy = int(h_ / 2.0f - K1 * ooz * point.y * 0.5f);   // minus: screen rows go DOWN
        if (sx < 0 || sx >= w_ || sy < 0 || sy >= h_) continue;

        // Z-buffer: only draw this point if it's closer than whatever is already in this cell.
        float& nearest = zbuf_[sy * w_ + sx];
        if (ooz <= nearest) continue;
        nearest = ooz;

        // Lighting: how much does the surface face the light? That's the dot product of the
        // normal with the light direction (0, 1, -1)/sqrt(2): up and towards the viewer.
        // Result is -1 (facing away) .. +1 (facing the light directly).
        const float luminance = (normal.y - normal.z) * 0.70710678f;
        const int shade = std::clamp(int(luminance * kNumShades), 0, kNumShades - 1);
        cv.set(sx, sy, kShades[shade], palette[shade]);
    }
}

Light. How bright a surface looks depends on how directly it faces the light (Lambert’s cosine law), and for two arrows of length 1 the cosine of the angle between them is their dot product. The light comes from above and towards the viewer, ℓ = (0, 1, −1)/√2, so

L=N·ℓ=Ny−Nz2

L runs from −1 (facing away) to +1 (facing the light), and picks one of twelve characters ordered from least ink to most. Each has its own colour, from dark chocolate in shadow to cream glaze in full light:

A bug worth understanding: sampling holes

The first version used fixed steps (θ += 0.07, φ += 0.02). When the donut tumbled towards you, dark specks appeared on its bright front. Its nearest part is at z = K2 − R1 − R2 = 2, where it looks 2.5 times bigger than at its centre, so neighbouring samples landed more than a cell apart. Some cells got no front point at all, and the z-buffer showed the shadowed back through the gap. Switch the panel to Old fixed steps to look for them. The fix works the steps out from the worst case, so that neighbours land less than 0.9 of a cell apart even where the donut is nearest:

Δθ=min(0.07,0.9znearestK1R1)Δφ=min(0.02,0.9znearestK1(R1+R2))

When you sample a continuous surface, the samples must be denser than the pixels where the surface looks biggest. A test that counted these holes found 395 in 600 frames at 100 × 29 before the fix, and none after. The flying donut uses the same rule with its current nearest point, so far away it needs fewer samples: flying is actually cheaper than spinning close up.

Flying round a figure-8

The same flying donut with its constants on sliders: kFlyZoom, kFogDensity, the 2 in sin(2 * t) and the pulse’s kSpringZeta. The program’s values are 2.5, 0.06, 2 and 0.38.

A path chosen directly in 3D makes it hard to keep the donut on screen, so the flight is designed in two parts, depth and screen position, and then turned into 3D:

z(t)=10−4cos⁡2tu(t)=roomx(z)sin⁡tv(t)=roomy(z)sin⁡2t

u and v are columns right of and rows below the window’s centre. v goes round twice while u goes round once, and that traces an 8: a Lissajous curve. t goes once from 0 to 2π every 12 seconds. The depth is smallest (6) each time the donut crosses the middle of the 8 and largest (14) at the ends of the two loops, so it swoops towards you through the centre and recedes into the distance at the sides. Try sin 3t in the panel for a different Lissajous figure.

To find the 3D centre that appears at (u, v), run the projection backwards:

sx=w2+K1xz⇒x=uzK1y=−2vzK1

How close to the edge?

room() answers one question: how far off-centre can the donut’s centre go with the whole donut still on screen? It is easiest in angles, as seen from the camera. The edge of the screen is at angle E off to the side, where tan E = edge / K1. The whole donut fits inside a ball of radius R1 + R2 = 3, and a ball of radius r at distance d covers an angle B either side of its centre, with sin B = r/d: those are the lines of sight that just touch it. So the centre can be at most E − B off to the side, and the subtraction formula for tangents turns that into cells:

tan⁡(E−B)=tan⁡E−tan⁡B1+tan⁡Etan⁡Broom=K1tan⁡(E−B)

A far-away donut covers a smaller angle, so it can get closer to the edge. That is why the room depends on z.

src/donut.cppVec3 flightCentre(double t) const {
    const float K1 = focal();
    const float z = 0.5f * (kNearZ + kFarZ) - 0.5f * (kFarZ - kNearZ) * float(std::cos(2 * t));
    if (K1 <= 0) return {0, 0, z};
    const float u = room(w_ / 2.0f - 1, K1, z) * float(std::sin(t));
    const float v = room(h_ / 2.0f - 1, K1 * 0.5f, z) * float(std::sin(2 * t));   // rows: y squashed by 0.5
    return {u * z / K1, -2 * v * z / K1, z};   // -2: rows go DOWN, and y was squashed by 0.5
}
src/donut.cppstatic float room(float edge, float K1, float z) {
    const float lens = K1 * kFlyZoom, d = z * kFlyZoom;
    const float tanE = edge / lens;
    const float tanB = kOuter / std::sqrt(d * d - kOuter * kOuter);
    return std::max(0.0f, lens * (tanE - tanB) / (1 + tanE * tanB));
}

A longer lens, and a dolly zoom

The classic camera is very close and very wide: about 108° across a 100-column window, like a phone’s 0.5× lens. Wide-angle pictures stretch whatever is near their edges, and the first flying version had a donut 1.8 times too wide at the ends of its loops.

So when flying, the camera moves kFlyZoom = 2.5 times further back and zooms in 2.5 times. K1 and every distance grow by the same factor, so the donut looks just as big and lands on the same cells, but the view is about half as wide and the stretching mostly goes away. Drag lens zoom down to 1× in the flight lab to see the stretched donut for yourself.

Doing both at once, while the donut glides out from the middle, is the dolly zoom film-makers use (Hitchcock’s Vertigo): the donut keeps its size while its perspective flattens.

Gliding, fading and the trail

Pressing M doesn’t teleport the donut. fly_ moves from 0 to 1 (or back) over 1.5 seconds, and the centre is mix(still, figure8, smoothstep(fly_)), with

smoothstep(t)=t2(3−2t)

It goes from 0 to 1 like t does, but starts and stops with zero speed, so the donut eases out and in instead of lurching.

Fog. Light crossing hazy air loses the same fraction of itself for every unit of distance, so what reaches you falls off exponentially: the Beer–Lambert law. The donut’s colours fade towards the black background by

brightness(z)=e−k(z−5),k=0.06

The trail is the last 75 centre positions (2.5 seconds), drawn as dots that fade with age. Each dot goes through the same z-buffer test as the donut, so the donut hides the dots behind it, and you can see the newest ones through its hole: the centre of a donut is in the middle of its hole.

The pulse: a spring and a blast wave

Each time the flying donut swoops through the middle of the 8, and whenever you press Space, it pulses like a drop hitting water: it pops, and ripple rings spread out from where it was. You can try it in the flight lab above, which also lets you change how bouncy the pop is.

The pop is a damped spring. The donut’s size is s = 1 + x, and x behaves like a weight on a spring with friction:

x¨=−ω02x−2ζω0x˙ω0=17rad/s,ζ=0.38

The spring pulls x back to 0, normal size, and the damping takes energy out. A pulse is a sudden kick to the speed, ẋ += 6.9 per second, like flicking the weight. ω0 sets how stiff the spring is, and ζ, the damping ratio, sets its character: at ζ = 0 it would wobble for ever, at ζ ≥ 1 it creeps back without overshooting, and in between it bounces. Each overshoot is the same fraction of the one before:

next overshootthis overshoot=e−πζ/1−ζ2

With ζ = 0.38 that fraction is 0.28, which gives the pop its natural feel: 1.25× after 75 ms, back down to 0.93× at 274 ms, and within 1% of normal by 541 ms. The same kind of springy overshoot is what makes animations on a phone feel physical.

src/donut.cppvoid pulse() {
    swellV_ = std::max(swellV_, 0.0) + kKick;   // a new kick always pops OUT, even mid-wobble
    rings_.push_back({centre(), 0});
    if (int(rings_.size()) > kMaxRings) rings_.erase(rings_.begin());
}

The spring is stepped in fixed 1 ms steps, like the pendulum, with semi-implicit Euler: it changes the speed first, then moves with the new speed. Plain Euler would work out both from the old values, and for an oscillator that slowly pumps energy in. With no damping, the wobble would grow by about 15% every second. Using the new speed costs nothing extra and doesn’t.

src/donut.cppvoid stepSpring(double h) {
    swellV_ += (-kSpringW0 * kSpringW0 * swell_ - 2 * kSpringZeta * kSpringW0 * swellV_) * h;
    swell_ += swellV_ * h;
}

A swollen donut is closer to you at its nearest point, so the sampling steps from the sampling-holes section use the swollen size, znearest = cz − (R1 + R2)·s. A test that compares frames against a much denser rendering found no new holes, and with no pulse the spin-in-place mode still draws exactly what the original program did.

The rings grow like a blast wave. A sudden burst of energy spreading into its surroundings slows down as it sweeps up more of them. For an explosion in open air the shock front’s radius grows as t2/5 (the Sedov–Taylor blast wave), and the rings use the same law, fading as they go:

r(t)=(R1+R2)(1.1+1.6(tT)0.4)brightness=(1−tT)2,T=1.2s

t0.4 starts infinitely fast and keeps slowing down, so a ring bursts out of the donut and drifts to a stop as it fades, drawn as ~ while it is bright, then -, then .. A second, fainter ring follows 0.15 s later, like the second ripple in a pond. On screen each ring is an ellipse twice as wide as it is tall, because the cells are twice as tall as they are wide. It stays where the splash happened while the donut flies on, and its dots go through the z-buffer, so the donut hides any part of a ring behind it.

[2]Matrix rain

matrix.cpp

The program’s four colour themes: green, cyan, amber and pink. Speed it up and the trails get longer, because a trail is as long as the distance a head falls in one second of fading.

The simplest of the four. It has two layers of state: one falling drop per column, each a position and a speed (these are particles), and for every cell a character and a brightness from 0 to 1. Each update(dt) does four things, in order:

  1. Everything fades. Brightness drops by 1 per second, so a lit cell lasts about a second.
  2. Drops fall, y += speed · dt. Every row the head moves into gets a fresh random character at full brightness. The loop covers every row between the old and the new head, so a fast drop never skips a cell.
  3. A drop that falls off the bottom respawns somewhere above the top. How far above decides how long that column stays dark.
  4. A few random cells change character, so the trails shimmer.
src/matrix.cpp// 2. Move each drop down. Every cell its head moves INTO lights up with a new character.
for (int x = 0; x < w_; ++x) {
    Drop& d = drops_[x];
    const int before = int(std::floor(d.y));
    d.y += d.speed * step;
    const int after = int(std::floor(d.y));
    for (int y = std::max(before + 1, 0); y <= after && y < h_; ++y) {
        glyph_[y * w_ + x] = randomGlyph();
        bright_[y * w_ + x] = 1.0f;
    }
    if (d.y >= h_) respawn(d);   // fell off the bottom: start again above the top
}

The trail isn’t stored anywhere as a trail. It is simply the cells the head lit recently that haven’t faded yet, so its length is speed ÷ fade rate: a drop falling 6 to 24 rows a second leaves a trail 6 to 24 rows long. When drawing, each brightness is rounded to 16 levels and blended from the theme’s dark colour to its bright one with linear interpolation, which turns up in almost every graphics program:

lerp(a,b,t)=a+(b−a)t

[3]Doom fire

fire.cpp

Press Space to turn the fuel off and watch the fire die from the bottom up, then again to relight it. The arrows change the flame height and the wind.

The fire from the PlayStation port of Doom (1995), made famous by Fabien Sanglard’s write-up. The screen is a grid of heat values from 0 (cold) to 1 (white-hot), and the whole algorithm is one rule:

bottom row = fuel = 1.0 (full heat) for every cell (x, y) except the top row: dx = random -1, 0 or +1 (plus an extra 1 sideways sometimes, if there is wind) above = cell (x + dx, y - 1) heat[above] = heat[x, y] - random(0 .. 2 * cooling)

Heat moves up a row each step, loses a random amount and wobbles sideways, and that looks like flames. A rule where each cell’s next value depends only on its neighbours is a cellular automaton; Conway’s Game of Life is another.

Flame height. Each row loses cooling heat on average, so heat that starts at 1 dies out after about 1/cooling rows. To make the flames reach heightFrac of the window, the program uses

cooling=1heightFrac·h

Why one array is enough. A grid update normally needs two arrays, old and new, so you never read a value you already changed this step. Here row y writes only into row y − 1, and the loop runs from the top down. When it reaches row y, nothing has written to that row yet this step (row y + 1 comes later), so every read sees last step’s value.

src/fire.cppvoid step() {
    // 1. Fuel row. When the fuel is off, let it die down gradually instead of all at once.
    float* fuel = &heat_[size_t(h_ - 1) * w_];
    for (int x = 0; x < w_; ++x) fuel[x] = burning_ ? 1.0f : std::max(0.0f, fuel[x] - 0.05f);

    // 2. Spread heat upwards. On average a cell loses 'cooling' per row, so the flames die out
    //    after about 1/cooling rows. Pick cooling so that's heightFrac_ of the window.
    const float cooling = 1.0f / (heightFrac_ * h_);
    // Go from the top row down. Row y writes into row y-1, and row y itself is only written
    // later (by row y+1), so we always read last step's value. That's why one array is enough.
    for (int y = 1; y < h_; ++y) {
        for (int x = 0; x < w_; ++x) {
            int dx = rng_.integer(-1, 1);                                   // random flicker
            if (rng_.uniform(0, 1) < std::abs(wind_)) dx += wind_ > 0 ? 1 : -1;   // steady wind
            const int dst = ((x + dx) % w_ + w_) % w_;                      // wrap around the edges
            const float h = heat_[y * w_ + x] - rng_.uniform(0, 2 * cooling);
            heat_[(y - 1) * w_ + dst] = std::max(0.0f, h);
        }
    }
}

Space turns the fuel off: the bottom row then cools gradually instead of staying at 1, and the fire dies from the bottom up, as on the Doom title screen. The 32 colours, from black through red, orange and yellow to white, are worked out once in the constructor, because looking them up is far cheaper than recomputing them for every cell of every frame. And the fire always steps 40 times a second, whatever the frame rate.

[4]Double pendulum

pendulum.cpp

Press I to switch to Euler and watch the drift number in the top line climb. T adds the twin.

Everything about the pendulum at one instant fits in four numbers: the two angles from straight down, θ1 and θ2, and how fast they are changing, ω1 and ω2. Both rods are 1 m long and both weights 1 kg. Lagrangian mechanics gives the angular accelerations, with Δ = θ1 − θ2:

θ¨1=−g(2m1+m2)sin⁡θ1−m2gsin⁡(θ1−2θ2)−2sin⁡Δm2(ω22L2+ω12L1cos⁡Δ)L1(2m1+m2−m2cos⁡2Δ) θ¨2=2sin⁡Δ(ω12L1(m1+m2)+g(m1+m2)cos⁡θ1+ω22L2m2cos⁡Δ)L2(2m1+m2−m2cos⁡2Δ)

derivative(s) returns how fast each part of the state is changing: (ω1, ω2, θ̈1, θ̈2). There is no formula for where the pendulum will be at time t. The only way to find out is to step forward in tiny steps, which is numerical integration.

src/pendulum.cppState derivative(const State& s) {
    const double d = s.th1 - s.th2;
    const double den = 2 * m1 + m2 - m2 * std::cos(2 * d);
    const double a1 = (-g * (2 * m1 + m2) * std::sin(s.th1) - m2 * g * std::sin(s.th1 - 2 * s.th2) -
                       2 * std::sin(d) * m2 * (s.w2 * s.w2 * L2 + s.w1 * s.w1 * L1 * std::cos(d))) /
                      (L1 * den);
    const double a2 = (2 * std::sin(d) *
                       (s.w1 * s.w1 * L1 * (m1 + m2) + g * (m1 + m2) * std::cos(s.th1) +
                        s.w2 * s.w2 * L2 * m2 * std::cos(d))) /
                      (L2 * den);
    return {s.w1, s.w2, a1, a2};
}

Euler and RK4

Explicit Euler follows the slope measured at the start of each step:

sn+1=sn+hf(sn)

Its error always leans the same way, and for this pendulum that means the energy creeps up. Runge–Kutta 4 measures the slope four times across the step and takes a weighted average:

k1=f(s) slope at the start k2=f(s+h2k1) at the middle, using k₁ k3=f(s+h2k2) at the middle again, using k₂ k4=f(s+hk3) at the end snext=s+h6(k1+2k2+2k3+k4)

Halve the step h and Euler’s error halves, while RK4’s shrinks 16 times: it is fourth order. The program steps h = 0.002 s, 500 times per simulated second, and the operator+ and operator* defined for State let the C++ read almost exactly like the maths:

src/pendulum.cpp// Explicit Euler: follow the slope at the START of the step. Simple, but the error always
// pushes the same way, so the energy slowly creeps up and the pendulum goes wild.
State stepEuler(const State& s, double h) { return s + h * derivative(s); }

// Classic 4th-order Runge-Kutta: measure the slope 4 times across the step (start, two guesses
// at the middle, end) and use a weighted average. Hugely more accurate for the same h.
State stepRK4(const State& s, double h) {
    const State k1 = derivative(s);
    const State k2 = derivative(s + (h / 2) * k1);
    const State k3 = derivative(s + (h / 2) * k2);
    const State k4 = derivative(s + h * k3);
    return s + (h / 6) * (k1 + 2 * k2 + 2 * k3 + k4);
}

Energy as a correctness test

There is no friction, so the total energy, kinetic plus potential, must never change:

T=12m1L12ω12+12m2(L12ω12+L22ω22+2L1L2ω1ω2cos⁡Δ) V=−(m1+m2)gL1cos⁡θ1−m2gL2cos⁡θ2

So any change in T + V is integrator error, and checking a quantity that physics says must stay constant is one of the best ways to test any simulation. Chaos: the twin

Press T in the panel to add a second pendulum, in blue, that starts 0.001 radians (0.06°) away from the first. For a few seconds they move as one. Then they separate, and soon they have nothing in common; the top lines of the panel show how far apart the lower weights are.

This is chaos. The motion is completely deterministic, with no randomness at all, yet tiny differences grow exponentially, so long-term prediction is impossible in practice. It isn’t numerical error either: RK4 is accurate here, and the physics itself magnifies the difference. The same butterfly effect is why weather forecasts stop being reliable after about a week.

Drawing it. The pivot is the centre of the grid, and one metre is rowsPerMetre rows down but twice as many columns across. Each rod is drawn by stepping along it one cell at a time (a DDA line), with -, /, | or \ picked from atan2(-dy * 2, dx), the ×2 again correcting for tall cells. The last 400 positions of the lower weight live in a std::deque, which adds at the back and drops from the front cheaply, and older points are drawn dimmer and smaller: *, then :, then ..

Two gotchas met along the way

The most vexing parse. This line was meant to make a Rotation object:

const Rotation rotA(float(angleA_));   // C++ reads this as a FUNCTION declaration!
const Rotation rotA{float(angleA_)};   // braces always mean "make an object"

The first line can also be read as “a function rotA taking a float parameter named angleA_”, and the C++ rules say that reading wins. When in doubt, initialise with braces.

Name hiding. While adding the flight, donut.cpp briefly had its own Vec3 lerp(Vec3, Vec3, float) beside the Color lerp(Color, Color, float) from terminal.h. Then lerp({90, 90, 90}, {255, 255, 255}, t) stopped compiling. A function declared inside a namespace hides every function of the same name from outside it, even ones with different parameter types, so the compiler only considered the Vec3 version. The point version is now called mix.
